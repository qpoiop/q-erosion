# 성능 & 재발 방지 — 구조적 방안

개별 증상을 하나씩 막는 방식(하드코딩 방어)은 금지. 아래는 **클래스 단위로 문제를 없애는** 방안.

## 왜 우리한테만 생겼나
일반 상용 웹게임은 (1) 에셋·드로우콜 예산이 파이프라인에 강제되고 (2) 넷코드가 스키마/틱 기반이며
(3) 성능 회귀가 CI에서 걸러진다. 우리는 기능을 빠르게 쌓으며 이 세 가지 계약이 없었다 — 그래서
"라이트 하나 추가", "메시지 하나 더" 같은 사소한 변경이 스파이크로 나타났다.

## 1. 렌더 계약 (3D)
- **불변 조명**: 씬 라이트는 초기화 시 고정. 동적 광원은 이미시브/헤일로로 표현 (셰이더 재컴파일 클래스 제거)
- **에셋 예산**: 배포 GLB는 개당 ≤1.5MB·텍스처 ≤512px·정적은 merge, 스킨드는 무가공 — 파이프라인 스크립트가 강제
- **오브젝트 예산**: 파티클(링 48/스파크 240)·탄환·바는 전부 풀. 신규 이펙트는 풀에 등록해야만 생성 가능
- **드로우콜 다이어트 로드맵**: 잡몹 InstancedMesh 전환(1 드로우콜/모델), 탄환 인스턴싱 — 480마리 시대의 다음 단계
- **거버너는 보험**: 자동 저사양 모드는 최후 방어선이지 해결책이 아니다. 예산 위반이 원인일 때 예산을 고친다

## 2. 넷 계약 (WebSocket)
- **틱 기반 송신만 허용**: 발생당 send 금지. 모든 이벤트는 큐(shotQ/hitQ/ebQ) → pose/state 틱에 플러시
- **평탄 스키마**: 반복 데이터는 stride-N 숫자 배열 (en=6, st=5). 중첩 배열/객체 금지 — 파싱·GC 비용이 곧 프레임
- **적응 케이던스**: 상태 크기에 비례해 주기 완화(적 60+/120+), 클라 보간이 흡수
- **버전 계약**: 와이어 변경 = PV 범프, 핸드셰이크에서 검증. "조용히 무시되는 메시지"는 버그로 취급
- **전송 이중화**: 우선 채널(DO 릴레이) + 폴백(MQTT)은 반드시 복귀 루프 보유, 매치메이킹은 양채널 병행

## 3. 시뮬 계약
- **핫루프 무할당**: 적×프레임 루프 안에서 배열/객체 리터럴 금지 (방향 상수 호이스트, 버퍼 재사용, Map 재활용)
- **판정 불변식**: 투사체=대상별 1회, 페이즈 분기=명시적, 상태 전이 메시지=페이즈 가드
- **리셋 완전성**: 게임 간 지속 상태는 _reset이 소유하는 단일 목록 — 새 상태 추가 시 여기부터

## 4. 프로세스 (재발 차단 장치)
- **최대부하 벤치를 릴리스 게이트로**: scratchpad의 stress 스위트(480마리+타워 40+실GPU)를 배포 전 실행,
  프레임 예산(평균 8ms/최악 33ms) 초과 시 배포 중단 — CI 잡으로 승격 예정
- **E2E 스위트 상시 실행**: verify-release / verify-mp-full(지갑·연구·재접속·일시정지) / verify-nm-inv
- **실기기 텔레메트리**: ?fps=1 미터. 이슈 리포트는 수치와 함께
- **관측 우선 디버깅**: 증상 재현 → 이분 탐색(기능 끄기) → 계측 확정 후 수정. 추측 패치 금지

## 5. 측정 기준선 (2026-07 기준, 실GPU)
- 480마리 enemySim 1.66ms / 최대부하 프레임 평균 4.1ms·최악 6.3ms
- 후반 메시지 ~19/s (배칭 후, 기존 ~50/s)
- 대량 킬 프레임 3.4ms (라이트 제거 후, 기존 243ms)

### 보스 텔레그래프 (계약 준수 사례)
- 바닥 게이지는 전부 **사전 생성 풀**(원판 5·직사각 1·링 밴드 4) + MeshBasicMaterial — 조명 미접촉, 셰이더 재컴파일 없음
- `_warmFx`에서 인트로 오버레이 뒤에 1프레임 플래시로 셰이더 워밍 (첫 캐스트 스톨 방지)
- 폭발 이펙트는 기존 _fx/_burst 풀 재사용, 신규 파티클 시스템 없음
